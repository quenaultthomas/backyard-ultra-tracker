# Increment R.3 : Menu burger utilisateur connecté

Troisième incrément du jalon R (refonte graphique). Il remplace, **pour l'utilisateur connecté**, les liens alignés de l'en-tête (pseudo, Administration / Espace bénévole / Espace coureur / Mes inscriptions, Mon compte, `bouton-deconnexion`) par le **menu burger** de R.2, généralisé : pseudo en tête (non cliquable), entrées selon le rôle, « Se déconnecter ». **Aucun back, aucun contrat d'API, aucune règle métier, aucune route, aucune garde, aucune migration, aucune variable d'environnement, aucune dépendance npm.**

## Ce qui est déjà livré (0.x à 3.6, R.1, R.2), donc non respécifié

Vérifié dans le code :
- `Entete` (`frontend/src/app/entete/entete.{ts,html,css}`, monté une fois dans `app.ts`) : un `@switch` sur `session.etat()`. `ANONYME` : `<app-menu-visiteur />` (R.2) ; `CONNECTE` : `entete-pseudo`, puis `lien-administration` (si `estAdministrateur`, donc `ADMIN` et `ADMIN_MASTER`), `lien-espace-benevole` (`estBenevole`), `lien-espace-coureur` et `lien-mes-inscriptions` (`estCoureur`), `lien-mon-compte` (tous), `bouton-deconnexion` (`class="entete__bouton"`, `[disabled]="envoiEnCours()"`, appelle `seDeconnecter()`). `INCONNU` : zone vide. Le message `entete-erreur` (`role="alert"`) est affiché sous l'en-tête quand la déconnexion échoue.
- `seDeconnecter()` : garde anti-double envoi (`envoiEnCours`), `session.deconnecter()` (POST de déconnexion + nouveau jeton CSRF), puis `navigateByUrl('/connexion')` où l'écran affiche `message-deconnexion` ; en échec : `CSRF_INVALIDE` -> `MESSAGE_PAGE_EXPIREE` + renouvellement du jeton, sinon `MESSAGE_SERVICE_INDISPONIBLE` ; l'état reste connecté et l'action peut être retentée. **Ce comportement est conservé tel quel.**
- Composant `MenuVisiteur` (`entete/menu-visiteur/`) : pattern « disclosure navigation », état `ouvert`, fermetures (Échap, `pointerdown` extérieur, `focusout` vers un élément extérieur, clic d'une entrée, `NavigationStart`, destruction), focus sur la première entrée à l'ouverture, `routerLinkActive` + `ariaCurrentWhenActive="page"`, bouton `bouton-menu` / `aria-label="Menu du compte"` / `aria-controls="entete-menu-panneau"`, icône « tête » inline, panneau `nav#entete-menu-panneau` toujours dans le DOM avec `hidden`. Règles RG4 à RG12 de R.2 : **réutilisées, non réécrites ici**.
- Routes et gardes : `/mon-compte` est gardé par `reserveAuxComptesConnectes` (`reserveAuxRoles(() => true)`) : **ouvert aux quatre rôles**. `/administration` : `reserveAuxAdministrateurs` ; `/benevole` : `reserveAuxBenevoles` ; `/coureur` et `/coureur/inscriptions` : `reserveAuxCoureurs`. Un rôle hors périmètre est envoyé vers `/acces-refuse`, un anonyme vers `/connexion?retour=…`.
- Pseudo (back, `Pseudo.java`) : 3 à 30 caractères, lettres Unicode, chiffres, `.`, `_`, `-`, sans espace ; un Compte anonymisé s'appelle « Coureur anonyme » (un coureur supprimé n'est plus connecté).
- Charte R.1 (`docs/design.md`, `frontend/src/styles/*`) : 18 couleurs, `--cible-min` 44 px, contour de focus orange dans `.entete`. `.entete__bouton` (`composants.css`) ne sert que pour `bouton-deconnexion`.

Taille estimée (production hors tests) : ~230 lignes, dont l'essentiel est un renommage / une généralisation du composant de R.2 : `menu-burger` (template ~60, classe ~85, CSS ~100 repris de R.2), `entrees-menu.ts` ~30, `entete.ts` ~15 (+/-), `entete.html` ~-35, `entete.css` ~-25, `composants.css` ~-18. Sous la cible (400) : pas de découpage.

## 1. Périmètre

**Inclus**
- Menu burger de l'utilisateur connecté : pseudo, entrées par rôle, « Se déconnecter » (RG3 à RG8).
- Généralisation du composant de R.2 en **un seul** composant `MenuBurger` (RG1) ; le menu visiteur devient une instance de ce composant, sans changement visible (RG2).
- Suppression des liens alignés de l'en-tête connecté et de leurs `data-testid` (RG9).
- Clavier, focus, fermetures, responsive, charte : **mêmes règles que R.2** (RG10), plus les cas propres (pseudo long, déconnexion).
- Adaptation des E2E existants (RG13, section 6).

**Exclu**
- Page d'accueil (indicateur API, doublon `lien-creer-compte`) : R.4. Écrans de connexion et de création de compte au nouveau thème, dont le débordement du `h1` `titre-connexion` à 200 % de texte à 320 px (point ouvert 13 de R.2) : **R.5**. Ce défaut est exclu des mesures de cet incrément (CA10).
- Toute nouvelle entrée de navigation (par exemple « Gestion des courses » ou « Tableau de bord » dans le menu), tout changement de route, de garde, de titre d'onglet, tout back.
- Menu pour l'état `INCONNU` ; mode sombre ; animations (finition R.9) ; bibliothèque de menus ou d'icônes ; tests unitaires front (interdits).

## 2. Règles de gestion

**Cadre**
- **RG1** : un seul composant de menu. `MenuVisiteur` est généralisé en `MenuBurger` (`app-menu-burger`, dossier `entete/menu-burger/`, qui remplace `menu-visiteur/`) : bouton, état, fermetures, focus, panneau et styles sont écrits **une seule fois**. Deux composants dupliqueraient ~100 lignes de comportement d'accessibilité (écouteurs, focus, fermetures) dont tout écart serait un défaut ; la différence entre visiteur et connecté n'est que des données. Entrées du composant : `nomPanneau` (nom accessible du `nav`), `testidPanneau`, `pseudo` (optionnel : s'il est fourni, la ligne pseudo est affichée), `entrees` (liste d'entrées ci-dessous), `actionEnCours` (booléen). Une entrée est soit un **lien** (`libelle`, `testid`, `route`), soit une **action** (`libelle`, `testid`) qui émet un événement `action` portant son `testid`. La liste par rôle est produite au seul endroit `entete/entrees-menu.ts` (fonction pure du rôle).
- **RG2** : l'état `ANONYME` est inchangé par rapport à R.2 : mêmes `data-testid` (`bouton-menu`, `menu-visiteur`, `menu-lien-se-connecter`, `menu-lien-creer-compte`), mêmes textes, même DOM visible, mêmes noms accessibles (`Menu du compte` pour le bouton, `Menu visiteur` pour le panneau), même comportement. Les classes CSS `menu-visiteur__*` et `entete--visiteur` sont renommées `menu-burger__*` et `entete--menu` (aucun E2E ne s'appuie sur une classe).
- **RG3** : affichage selon `session.etat()` : `INCONNU` : **rien** (inchangé, jusqu'à 5 s) ; `ANONYME` : menu visiteur ; `CONNECTE` : menu connecté. Chaque état instancie **sa propre instance** du composant (blocs `@case` distincts) : un changement d'état détruit l'instance précédente (écouteurs retirés) et la nouvelle naît **fermée** (réutilise RG7 / RG8 f de R.2). L'en-tête est en `flex-wrap: nowrap` dès que l'état n'est pas `INCONNU`.

**Contenu du menu connecté**
- **RG4** : le panneau est `<nav id="entete-menu-panneau" aria-label="Menu utilisateur" data-testid="menu-compte">`, mêmes `hidden`, `id` et position que R.2. Le bouton est identique à R.2 (`bouton-menu`, icône « tête », `aria-label="Menu du compte"`, `aria-expanded`, `aria-controls`). Le panneau contient, dans l'ordre : (1) la ligne pseudo (RG5), (2) une liste `<ul>` des entrées (RG6).
- **RG5** : pseudo. `<p class="menu-burger__pseudo">` placé **avant** la liste (donc hors de la liste : le lecteur d'écran annonce une liste du nombre réel d'entrées). Il contient un texte masqué visuellement « Connecté en tant que » (classe locale de masquage, lu par les lecteurs d'écran) puis `<span data-testid="entete-pseudo">` portant le pseudo, **inchangé** (même `data-testid` que l'ancien pseudo de l'en-tête, pour que les ~60 assertions de connexion de l'E2E restent valides : `toHaveText(pseudo)` et `toHaveCount(0)` fonctionnent aussi menu fermé). Le pseudo n'est **ni lien, ni bouton, ni focusable** (pas de `tabindex`, pas de `role`, pas de `cursor: pointer`, pas de fond au survol) ; un clic dessus laisse le menu ouvert et ne navigue pas. Texte brut (interpolation, jamais `innerHTML`). Style : graisse 700, couleur crème, `padding: var(--espace-3) var(--espace-4)`, filet bas 1px `--couleur-foret-survol`, `overflow-wrap: anywhere` : un pseudo long **passe à la ligne, il n'est jamais tronqué** (pas de points de suspension : le texte complet reste lisible et annoncé), le panneau restant borné au viewport (RG10 de R.2 : `max-width: calc(100vw - 2 * var(--espace-4))`).
- **RG6** : entrées par rôle (rôles exclusifs, un compte n'en a qu'un). Ordre fixe, `data-testid` exacts :

  | Rôle | Entrées dans l'ordre (libellé, `data-testid`, destination) |
  |---|---|
  | `COUREUR` | « Espace coureur » `menu-lien-espace-coureur` `/coureur` ; « Mes inscriptions » `menu-lien-mes-inscriptions` `/coureur/inscriptions` ; « Mon compte » `menu-lien-mon-compte` `/mon-compte` ; « Se déconnecter » `bouton-deconnexion` (action) |
  | `ADMIN` et `ADMIN_MASTER` | « Administration » `menu-lien-administration` `/administration` ; « Mon compte » `menu-lien-mon-compte` ; « Se déconnecter » `bouton-deconnexion` |
  | `BENEVOLE` | « Espace bénévole » `menu-lien-espace-benevole` `/benevole` (**seule entrée actuelle du bénévole**, relevée dans `entete.html` ; ne pas en inventer) ; « Mon compte » `menu-lien-mon-compte` ; « Se déconnecter » `bouton-deconnexion` |

  « Mon compte » existe pour **les quatre rôles** : la route `/mon-compte` est gardée par `reserveAuxComptesConnectes`, qui accepte tout compte connecté (changement de mot de passe et suppression du compte : comportement de 3.x inchangé, y compris la restriction côté back pour l'admin master, non touchée ici). ADMIN_MASTER et ADMIN ont exactement les mêmes entrées (les sous-écrans `administration/admins`, `/benevoles`, `/courses` restent atteints depuis l'écran Administration, comme avant). Un rôle ne voit jamais l'entrée d'un autre rôle : l'absence est un `toHaveCount(0)`, pas un masquage (l'élément n'existe pas dans le DOM).
- **RG7** : « Se déconnecter » est un `<button type="button" data-testid="bouton-deconnexion">` dans un `<li>` comme les liens, rendu comme une ligne d'entrée (mêmes hauteur >= 44 px, padding, couleur crème, graisse 600, survol / focus : fond `--couleur-foret-survol` et soulignement ; fond transparent, sans bordure, `width: 100%`, texte aligné à gauche, `font: inherit`). L'ancien style `.entete__bouton` (bouton secondaire bordé) est supprimé de `composants.css` et de `docs/design.md` (plus aucun usage). Le bouton est désactivé (`disabled`) tant que `actionEnCours` est vrai. À l'activation (clic, Entrée, Espace) : le menu se ferme, **le focus est rendu à `bouton-menu`** (l'élément activé vient d'être masqué, sinon le focus tomberait sur `body`), puis `seDeconnecter()` s'exécute **sans modification** : navigation vers `/connexion` après succès avec `message-deconnexion` ; en échec, `entete-erreur` s'affiche (messages inchangés), l'utilisateur reste connecté, le focus est sur `bouton-menu`, et il peut rouvrir le menu et réessayer. Après un succès, le menu connecté est détruit (RG3) : le focus n'est pas forcé (comme avant, quand le bouton disparaissait).
- **RG8** : page courante. Chaque entrée **lien** porte `aria-current="page"` et la classe de page courante (graisse 700, filet gauche 4px `--couleur-orange`, R.2 RG6) **uniquement si son URL correspond exactement** à l'URL courante (`routerLinkActiveOptions: { exact: true }`) : sur `/coureur/inscriptions`, seul « Mes inscriptions » est courant, pas « Espace coureur » (`/coureur`) ; sur `/administration/courses`, aucune entrée n'est courante (« Administration » désigne `/administration` seulement). Le pseudo et « Se déconnecter » ne sont jamais courants. Sélectionner l'entrée de la page courante ne change pas l'URL et ferme le menu.

**Suppression des liens alignés, tests, charte**
- **RG9** : disparition. En état `CONNECTE`, l'en-tête ne contient plus que `entete-titre`, `bouton-menu`, le panneau `menu-compte` (et `entete-erreur` quand elle s'affiche). Les `data-testid` `lien-administration`, `lien-espace-benevole`, `lien-espace-coureur`, `lien-mes-inscriptions`, `lien-mon-compte` n'existent plus nulle part (vérifié : seul `entete.html` les portait). `bouton-deconnexion` et `entete-pseudo` sont **conservés** (RG5, RG7). Data-testid nouveaux exacts : `menu-compte`, `menu-lien-administration`, `menu-lien-espace-benevole`, `menu-lien-espace-coureur`, `menu-lien-mes-inscriptions`, `menu-lien-mon-compte`. Aucun n'entre en collision avec un `data-testid` de page (le préfixe `menu-lien-` distingue des `lien-*` des écrans).
- **RG10** : réutilisation intégrale de R.2 pour le menu connecté, sans réécriture : état fermé au chargement et après navigation (RG7), fermetures Échap / appui extérieur non consommé / sortie du focus (`relatedTarget` non nul) / sélection / changement de route / changement d'état de session (RG8), Échap rend le focus au bouton (RG9), aucun piège de focus, double activation = fermé (RG11), focus à l'ouverture sur **la première entrée** (RG10 de R.2) qui est ici la première entrée interactive du panneau (premier `a` ou `button`), **jamais le pseudo**. Ordre de Tab : titre, bouton, entrées (menu ouvert), contenu de la page.
- **RG11** : clavier, **tranche le point ouvert 2 de R.2** : pas de flèches, ni Début / Fin, ni saisie de lettres : Tab et Maj+Tab suffisent (au plus 4 entrées interactives, le pseudo n'est pas focusable), le pattern « disclosure navigation » est conservé. Le pattern `menu` / `menuitem` est écarté car 3 des 4 entrées sont de la navigation, et il imposerait un focus itinérant et le passage des lecteurs d'écran en mode application pour un gain nul à ce nombre d'entrées. « Se déconnecter » est une commande dans un panneau de navigation : accepté (la disclosure admet des boutons ; usage répandu), activable à Entrée et Espace.
- **RG12** : charte et responsive. Mêmes règles qu'en R.2 (RG3, RG6, RG12, RG13) : cibles >= 44 px (lignes entières, y compris `bouton-deconnexion`), texte >= 13 px, contrastes AA (crème / forêt 11,86 ; crème / forêt-survol 7,17), contour de focus orange 3px, aucune couleur en dur ni hors des 18 de R.1, aucune transition. À 320, 360 et 1280 px : aucun défilement horizontal de la page entière, panneau entièrement dans le viewport. À 320 px avec le texte à 200 % (`font-size` racine 32 px) : mesures **sur l'en-tête et sur le panneau uniquement**, pas sur la page entière (leçon de R.2 : le `h1` de `/connexion` y déborde, R.5). Panneau connecté plus haut que le viewport (4 entrées + pseudo à 200 %) : il reste dans la largeur ; sa hauteur est bornée (`max-height: calc(100vh - 100%)` avec défilement vertical interne `overflow-y: auto`) pour que chaque entrée reste atteignable. `forced-colors` : bordure et icône suivent `currentColor`.
- **RG13** : non-régression E2E. Les E2E existants qui s'appuient sur l'en-tête connecté sont **adaptés, jamais supprimés ni affaiblis** (tableau ci-dessous). Règle de tri : (a) tout `bouton-menu` qui servait de signal « anonyme » (R.2) ne discrimine plus (il existe aussi connecté) : il devient `menu-visiteur` (présent, `toHaveCount(1)`) pour « anonyme » et `menu-visiteur` `toHaveCount(0)` pour « connecté » ; un `toBeVisible` sur `bouton-menu` est **complété** (jamais remplacé) par ce contrôle ; (b) toute interaction ou `toBeVisible` sur un élément du menu connecté est précédé de `ouvrirMenuCompte(page)` ; (c) tout `toHaveCount(0)` d'un ancien `lien-*` devient le `menu-lien-*` équivalent (sinon l'assertion passerait à vide) ; (d) `entete-pseudo` `toHaveText` / `toHaveCount(0)` : inchangés ; (e) quand le menu doit rester ouvert pour une assertion et que le test poursuit sur la page, il est refermé par Échap (aide `fermerMenuCompte`) pour qu'il ne masque pas le contenu.
- **RG14** : `docs/design.md`, section « Composants » : le paragraphe « Menu burger de l'en-tête » est généralisé (visiteur et connecté, un composant, pseudo, entrées par rôle, `bouton-deconnexion` en ligne d'entrée, pattern disclosure et décision sur les flèches) ; la ligne « En-tête » ne mentionne plus de liens orange ni de bouton secondaire ; `.entete__bouton` est retiré. Aucun autre fichier de `docs/` n'est modifié (ni le roadmap ni les specs précédentes).

## 3. Cas limites

- **Pseudo de 30 caractères** (limite du back) avec `.`, `_`, `-` et lettres accentuées (ex. `ZZZZZZZZZZZZZZZZZZZZZZZZZZ.é_-`) : sur une seule ligne si la largeur le permet, sinon coupé à la ligne (`overflow-wrap: anywhere`), jamais tronqué ni débordant du panneau, y compris à 320 px et 200 % de texte. Le pseudo est du texte : aucun caractère n'est interprété comme balisage. Les pseudos acceptés par le back ne contiennent ni espace ni chevron, mais le rendu reste en interpolation par principe.
- **Pseudo très court** (3 caractères) : le panneau garde `min-width: 14rem`.
- **Rôle** : un rôle ne voit que ses entrées (RG6) ; un anonyme ne voit aucune entrée de compte ; un coureur qui saisit `/administration` dans la barre d'adresse est envoyé sur `/acces-refuse` (garde existante, inchangée) et son menu reste celui d'un coureur. ADMIN et ADMIN_MASTER voient le même menu.
- **Page courante** : `/coureur` -> seul « Espace coureur » est courant ; `/coureur/inscriptions` -> seul « Mes inscriptions » ; `/mon-compte` -> « Mon compte » ; `/administration` -> « Administration » ; `/administration/courses`, `/benevole` pour un admin (refusé), `/` , `/acces-refuse` -> aucune entrée courante.
- **Menu ouvert pendant que la session expire** (une requête reçoit 401 -> `oublierSessionExpiree()`) : l'état devient `ANONYME`, le menu connecté est détruit, le menu visiteur apparaît **fermé** ; aucun focus forcé ; l'écran protégé est traité par les gardes comme avant.
- **Menu ouvert, déconnexion lancée dans un autre onglet** : rien ne change tant qu'aucune requête n'est émise (comportement existant).
- **Déconnexion** : double activation impossible (le menu se ferme à la première, garde `envoiEnCours` conservée) ; échec réseau ou CSRF : `entete-erreur` s'affiche, le menu est fermé, l'utilisateur reste connecté, nouvelle tentative possible (RG7) ; succès : `/connexion` avec `message-deconnexion`, menu visiteur fermé, aucun pseudo.
- **Connexion pendant que le menu visiteur est ouvert** (soumission lancée avant la réponse) : le menu visiteur est détruit, le menu connecté naît fermé (RG3, comportement R.2 CA9 conservé).
- **Changement de route avec le menu ouvert** (retour arrière, clic du titre, garde) : fermé (R.2 RG8 e). **Navigation par une entrée** : le menu se ferme, le focus suit la navigation normale.
- **Tab depuis la dernière entrée** (`bouton-deconnexion`) : le focus sort, le menu se ferme ; **Maj+Tab depuis la première entrée** : retour au bouton, menu ouvert ; **Maj+Tab depuis le bouton ouvert** : titre, menu fermé (R.2). Le pseudo est sauté par Tab.
- **Appui sur le pseudo ou sur le filet** : n'est pas une fermeture (c'est dans le panneau), aucune action. Appui extérieur : ferme et agit sur l'élément visé (R.2 point ouvert 9).
- **Zoom 200 % à 320 px** : titre sur deux lignes, bouton à droite dans la bande du titre, panneau dans la largeur, hauteur bornée avec défilement interne, entrées >= 44 px. Redimensionnement avec le menu ouvert : conservé (R.2).
- **`INCONNU`** : titre seul, aucun burger ; le bon menu apparaît dès que l'état est connu, fermé. Un utilisateur déjà connecté ne voit donc jamais passer le menu visiteur.
- **Utilisateur connecté qui ouvre `/connexion` ou `/creer-compte`** : redirigé vers `/` (garde), menu connecté.
- **Compte anonymisé (3.6)** : la session est fermée à la suppression ; un menu « Coureur anonyme » n'est jamais affiché.
- **Non applicables** (aucune règle ni donnée métier ne change) : Boucle, Passage, vainqueurs partagés, `CORRECTION` vs `SCAN`, plusieurs Courses, Course non démarrée, Inscription sans Passage, Réintégration, bénévole non affecté (les entrées et les accès aux écrans sont inchangés : seule leur présentation change).

## 8. Points ouverts

Bloquants : aucun. Positions par défaut appliquées dans la spec.

1. **Flèches (point ouvert 2 de R.2).** Position retenue : **pas de flèches**, disclosure + Tab (au plus 4 entrées interactives, pseudo non focusable). Alternative : pattern `menu` / `menuitem` complet. À confirmer.
2. **Pseudo visible seulement menu ouvert.** Conséquence de la roadmap : un utilisateur connecté ne voit plus son pseudo dans la barre. Alternative : pseudo (tronqué) à côté de l'icône. À confirmer.
3. **Pseudo long : retour à la ligne, jamais de troncature** (retenu). Alternative : points de suspension avec `title` (moins accessible).
4. **« Se déconnecter » : ligne d'entrée, plus de bouton bordé.** Les assertions de bordure crème de `theme-composants.spec.ts` sont remplacées par l'égalité de style avec une entrée (RG13). À valider avec l'utilisateur ; sinon, conserver un bouton bordé dans le panneau.
5. **Commande dans une navigation.** « Se déconnecter » est un bouton dans un `nav` de liens (disclosure admet les boutons). Alternative : séparateur visuel au-dessus de « Se déconnecter » (non retenu, ajouterait un filet).
6. **Focus à l'ouverture sur la première entrée** (position de R.2, point ouvert 3, reconduite), jamais sur le pseudo.
7. **Page courante exacte** (`/administration/courses` ne marque aucune entrée). Alternative : marquer « Administration » pour tout `/administration/**` (écart sémantique avec `aria-current="page"`).
8. **Pas de nouvelle entrée** (ex. liens directs vers « Gestion des courses » pour l'admin, écran de scan pour le bénévole) : le roadmap n'en prévoit pas ; à décider avec les écrans concernés.
9. **Nom accessible du panneau connecté** : « Menu utilisateur » (le bouton garde « Menu du compte », point ouvert 1 de R.2). À confirmer.
10. **Mon compte de l'admin master** : l'entrée est affichée pour tous (la route est ouverte à tout compte connecté) ; le comportement de l'écran pour l'admin master n'est pas modifié ici.
11. **Défaut `h1` de `/connexion` à 200 % (point ouvert 13 de R.2)** : exclu, traité en R.5 ; les mesures à 200 % portent sur l'en-tête et le panneau.
12. **Anciennes specs** (1.x, 3.x, R.1, R.2) citant les liens alignés : non modifiées (historique) ; la référence est cette spec. Le roadmap n'est pas modifié.
13. **Taille.** ~230 lignes de production (majorité de renommage) : pas de découpage.
