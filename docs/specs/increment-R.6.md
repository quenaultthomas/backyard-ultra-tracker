# Increment R.6 : Mon compte, changement de mot de passe repliable

Sixième incrément du jalon R (refonte graphique). Sur l'écran Mon compte (`/mon-compte`), le formulaire de changement de mot de passe est **replié par défaut** derrière un bouton de section dépliable (`aria-expanded`). Il se referme après un changement réussi (avec confirmation) et reste déplié en cas d'erreur. **Aucun changement de comportement métier, aucun back, aucun contrat d'API, aucune route, aucune garde, aucune migration, aucune variable d'environnement, aucune dépendance npm, aucun changement de Caddyfile. La section « Supprimer mon compte » ne change pas.**

## 2. Règles de gestion

**État et structure**
- **RG1** : replié par défaut. À chaque arrivée sur `/mon-compte` (navigation, rechargement, retour arrière, retour après reconnexion), pour **tout rôle connecté**, la section « Changer mon mot de passe » est repliée : le bouton de section est visible avec `aria-expanded="false"` ; le panneau (le formulaire) n'est **ni visible ni dans l'arbre d'accessibilité ni atteignable au clavier** : ses trois champs, l'aide `mon-compte-aide` et `mon-compte-bouton-changer` ne sont pas visibles, ne reçoivent pas le focus au Tab. Aucun message d'erreur ni de succès n'est affiché à l'arrivée. L'identité (`mon-compte-pseudo`, `mon-compte-role`) et, pour un coureur, la section de suppression restent visibles, inchangées.
- **RG2** : structure et accessibilité. Le titre `h2.sous-titre#titre-changer-mot-de-passe` **contient** un `<button type="button" data-testid="mon-compte-bouton-deplier">` au libellé exact « Changer mon mot de passe » (le titre de section reste un titre ; le nom accessible du bouton est ce libellé). Le bouton porte `aria-expanded="false"` / `"true"` (attribut toujours présent, valeurs textuelles `true` / `false`) et `aria-controls` = l'identifiant du panneau. Le panneau est le `form.formulaire` existant, désormais identifié (`id="panneau-changer-mot-de-passe"`, `data-testid="mon-compte-panneau-mot-de-passe"`) ; **il reste dans le DOM en permanence** (l'identifiant visé par `aria-controls` existe toujours) et est masqué à l'état replié par `display: none` effectif (valeur calculée mesurable, y compris malgré `.formulaire { display: flex }` : voir « Piège » ci-dessus), pas par `@if`. Conséquence voulue : les champs restent des éléments du DOM (valeur lisible et vide après un succès). `aria-labelledby` du formulaire (`titre-changer-mot-de-passe`) est conservé. Autour du titre et du panneau, une `section` (`aria-labelledby="titre-changer-mot-de-passe"`) les regroupe avec le message de succès (RG5). Aucun `svg`, `img` ni `canvas` dans le bouton (règle de `docs/design.md`, section 10) : le chevron est un pseudo-élément CSS décoratif, sans texte.
- **RG3** : dépliage. Un clic, la touche Entrée ou la touche Espace sur le bouton de section alternent l'état (bascule) : dépliage = `aria-expanded="true"`, panneau visible (display `flex`), contenu **identique** à celui d'avant R.6 (même ordre : champ actuel, champ nouveau avec son aide, champ confirmation, bouton « Changer le mot de passe » ; mêmes libellés, mêmes `data-testid`, mêmes attributs ARIA, champs vides). Le dépliage ne fait **aucun appel réseau** et **efface le message de succès** d'un changement précédent (RG5). **Le focus reste sur le bouton de section** (disclosure standard) ; le Tab suivant atteint le champ « Mot de passe actuel » (le panneau suit immédiatement le bouton dans l'ordre du DOM). Ordre de tabulation complet déplié : bouton de section, champ actuel, champ nouveau, champ confirmation, `mon-compte-bouton-changer`, puis (coureur) `mon-compte-bouton-supprimer`. Replié : bouton de section, puis (coureur) `mon-compte-bouton-supprimer`.
- **RG4** : repli manuel. Un second clic / Entrée / Espace sur le bouton replie le panneau (`aria-expanded="false"`, `display: none`). Le repli **vide les trois champs, efface tous les messages d'erreur (de champ et général) et l'état « soumis »** : les mots de passe saisis ne restent jamais en mémoire dans un panneau caché (cohérent avec `terminerEnvoi()`), et un nouveau dépliage affiche un formulaire vierge, sans message. Le repli n'émet aucune requête. Le focus **reste sur le bouton de section** (il l'avait, le clic s'y étant produit), jamais perdu sur `body`.
- **RG5** : succès. Quand `PUT /api/comptes/moi/mot-de-passe` aboutit : le panneau **se referme** (`aria-expanded="false"`, `display: none`), les trois champs sont vides, et le message `mon-compte-message-succes` (« Votre mot de passe a été modifié. », `role="status"`, style `.message-succes`) est affiché **dans la section, hors du panneau** (entre le titre-bouton et le panneau, donc visible alors que le panneau est caché) ; le **focus est placé sur le bouton de section** (le bouton qui avait le focus, « Changer le mot de passe », vient d'être masqué : sans cette règle le focus tomberait sur `body`). Le focus est posé **après** la réactivation du bouton de section (RG7), un bouton désactivé ne prenant pas le focus. Le message reste affiché jusqu'au prochain dépliage (RG3), jusqu'à une nouvelle soumission, ou jusqu'à la sortie de l'écran ; il ne disparaît pas tout seul. Le reste du comportement de succès (autres sessions fermées, session courante conservée, entête inchangé) est celui d'avant.
- **RG6** : erreur. En cas d'erreur de validation côté client (soumission à vide, nouveau < 12 caractères, confirmation différente), d'erreur serveur (mot de passe actuel incorrect, nouveau identique, 128 caractères dépassés, tentatives excessives, 500, erreur réseau, jeton CSRF expiré) : le panneau **reste déplié** (`aria-expanded="true"`), le message exact d'avant (liste ci-dessus) est affiché dans le panneau à l'endroit d'avant (`mon-compte-erreur-actuel`, `-nouveau`, `-confirmation`, `mon-compte-erreur-generale`), aucun message de succès n'est affiché, et les champs sont vidés comme avant (`terminerEnvoi()`, inchangé pour une erreur serveur ; la validation client n'envoie rien et ne vide rien, inchangé). La 401 redirige vers la connexion comme avant. Un message de succès précédent est effacé dès la nouvelle soumission (inchangé). Le focus après une erreur n'est pas modifié par R.6 (voir point ouvert 4).
- **RG7** : envoi en cours. Pendant l'envoi, le bouton de section est **désactivé** (`disabled`, style désactivé de la charte : fond `--couleur-desactive-fond`, texte `--couleur-desactive-texte`, curseur `wait`), en plus de `mon-compte-bouton-changer` (désactivé comme avant) : le panneau ne peut pas être replié pendant qu'une requête est en cours. Il est réactivé à la fin de l'envoi, succès ou erreur.
- **RG8** : comportement d'envoi inchangé. Mêmes validations, mêmes messages, même requête (`PUT /api/comptes/moi/mot-de-passe`, corps `{ motDePasseActuel, nouveauMotDePasse }`), même jeton CSRF, mêmes erreurs et codes, même blocage commun après cinq échecs, même fermeture des autres sessions. Aucune requête n'est ajoutée ni retirée. Un mot de passe n'apparaît dans aucune URL, aucun log, aucun `data-testid`, aucun attribut.
- **RG9** : suppression du compte inchangée. `app-suppression-compte`, son DOM, ses `data-testid`, ses textes, son style (`border-top`, `padding-top`), son comportement (confirmation, focus sur le champ à l'ouverture, annulation, suppression, redirection vers `/connexion`, message « Votre compte a été supprimé. ») sont **identiques** à ceux d'avant R.6. Elle est indépendante de l'état du panneau de mot de passe : ouvrir l'un n'ouvre, ne ferme et ne vide pas l'autre. Elle n'est affichée que pour un coureur (`estCoureur()`), inchangé : `BENEVOLE`, `ADMIN` et `ADMIN_MASTER` voient la section de mot de passe repliable et pas la suppression. Seule modification de `suppression-compte.*` : **aucune** (les fichiers ne changent pas). Le `overflow-wrap` de RG11 est hérité par cette section sans changer son rendu hors débordement.

**Mise en page et thème**

La carte (`.carte`) garde `gap: var(--espace-5)` (20 px) entre ses enfants : identité, section « mot de passe », suppression. La section « mot de passe » est une colonne flex à `gap: var(--espace-4)` (16 px). ## 3. Cas limites

- **Arrivée sur l'écran** : toujours replié, quel que soit l'état précédent (après un succès, une erreur, un rechargement, `goBack`/`goForward`, une reconnexion après 401 avec retour). Pas de persistance.
- **Clavier** : Entrée et Espace sur le bouton de section basculent (comportement natif de `<button>`), sans soumettre de formulaire (`type="button"`) ; Tab / Maj+Tab suivent l'ordre de RG3 ; le panneau replié n'est jamais atteignable au Tab (un champ en `display: none` n'est pas focusable). Depuis le premier champ, Maj+Tab revient au bouton de section ; replier avec Entrée depuis le bouton laisse le focus sur le bouton. Échap n'a aucun effet sur la section (le focus ne bouge pas, rien ne se replie). Entrée dans un champ soumet le formulaire comme avant.
- **Focus après repli** : repli manuel : focus sur le bouton de section (déjà là). Repli après succès : focus placé sur le bouton de section, après sa réactivation (RG5, RG7). Il n'est jamais sur `body`. Pas de saut de focus à l'ouverture (RG3).
- **`aria-expanded` / `aria-controls`** : `aria-expanded` reflète l'état réel à tout instant (y compris pendant l'envoi, où il reste `true`) ; `aria-controls` vise un identifiant présent dans le DOM dans les deux états (RG2). Le titre `h2` reste un titre dans l'arbre d'accessibilité (niveau 2) ; le bouton y est nommé « Changer mon mot de passe ». Le lecteur d'écran annonce le succès par `role="status"` (message hors panneau donc non masqué) et les erreurs par `role="alert"`.
- **Double clic rapide sur le bouton de section** : bascule deux fois, retour à l'état initial, sans erreur ni requête ; le repli vide les champs (RG4).
- **Saisie puis repli** : champs et erreurs vidés au repli, y compris des erreurs serveur affichées (RG4). Le message de succès précédent n'est pas réaffiché.
- **Succès puis dépliage** : le message de succès disparaît, formulaire vierge.
- **Succès puis nouvelle soumission** : nouveau cycle ; en cas d'erreur à la seconde soumission, panneau déplié et aucun message de succès (RG6).
- **Envoi en cours** : bouton de section désactivé (RG7) ; double clic sur « Changer le mot de passe » = un seul envoi (inchangé). Réponse lente (1 s) : le panneau reste déplié jusqu'à la réponse.
- **Erreur 401 pendant l'envoi** : redirection vers `/connexion?retour=%2Fmon-compte` ; au retour l'écran est replié (arrivée).
- **Blocage après cinq échecs** (429) : message général « Trop de tentatives. Réessayez dans 15 minutes. » dans le panneau déplié, qui reste déplié.
- **Jeton CSRF expiré** : message d'erreur général, nouveau jeton demandé (inchangé), panneau déplié.
- **Rôles** : coureur (section de mot de passe + suppression), bénévole, admin, admin master (section de mot de passe seule). Anonyme : redirigé vers la connexion (inchangé). Rôle insuffisant : sans objet (l'écran est ouvert à tout compte connecté ; l'API `PUT` exige une session, inchangé).
- **Menu burger ouvert** : un clic sur le bouton de section ferme le menu (appui extérieur, R.3) **et** bascule la section ; aucun conflit. Le menu burger ne doit pas être gêné par le panneau.
- **Gestionnaire de mots de passe du navigateur** : champs `display: none` quand replié ; ils ne sont pas pré-remplis tant que le panneau est caché. Les attributs `autocomplete` ne changent pas.
- **Suppression du compte** : la section de suppression suit le panneau de mot de passe dans la carte (déplié ou non) ; sa confirmation ouverte et le panneau ouvert coexistent ; la confirmation vide son propre champ à l'annulation sans toucher au panneau (RG9). Les deux champs « mot de passe actuel » (`current-password`) ont des `id` distincts (`mot-de-passe-actuel`, `mot-de-passe-suppression`), inchangés.
- **320 px / 200 %** (RG11) : libellé du bouton sur plusieurs lignes, chevron à droite sans chevauchement (le chevron est `flex: none`), message de succès et erreurs dans la carte, pseudo long (30 caractères) dans l'identité (règle existante) ; défilement vertical admis, jamais horizontal.
- **360 x 640 et paysage 640 x 360** : carte `clientWidth - 32` ; défilement vertical admis ; cibles >= 44 px.
- **Contraste forcé / mouvement réduit** : RG12.
- **Réseau** : l'écran ne charge rien de plus ; aucune requête n'est émise au dépliage / repli.
- **Non applicables** (aucune donnée métier ne change) : Boucle (au sens métier), Passage, vainqueurs partagés, `CORRECTION` vs `SCAN`, plusieurs Courses, Course non démarrée, Inscription sans Passage, Réintégration, nombre maximum de boucles, bénévole non affecté à une Course, instants de bascule de Boucle. `/api/test/horloge` inutile.

## 8. Points ouverts

Bloquants : aucun. Positions par défaut appliquées dans la spec.

1. **`overflow-wrap: anywhere` sur toute la carte de Mon compte (RG11).** Position retenue : la règle est posée sur la `.carte` de Mon compte (3 lignes dans `mon-compte.css`), ce qui corrige aussi, au passage, le titre « Mon compte » (56 px à 200 %) et le bouton « Changer le mot de passe » qui débordent à 320 px / 200 %, d'après le calcul de la zone utile (158 px) ; ce débordement n'avait pas été relevé en R.2 / R.5 (seule la connexion l'avait été) et est hérité par la section de suppression sans modifier ses fichiers. Alternative plus étroite : ne couvrir que la section « mot de passe » et laisser le reste de l'écran en l'état. À confirmer ; si le testeur constate d'autres débordements pré-existants sur l'écran (hors section), il les signale à l'orchestrateur plutôt que d'étendre l'incrément.
2. **Le focus reste sur le bouton au dépliage (disclosure standard) plutôt que d'aller sur le premier champ.** La suppression du compte, elle, envoie le focus dans son champ à l'ouverture. Position retenue : focus conservé sur le bouton, le Tab suivant atteint le premier champ ; c'est le comportement du pattern WAI-ARIA et celui du menu de l'en-tête. Alternative : focus sur « Mot de passe actuel » pour s'aligner sur la suppression. À valider à la recette.
3. **Le repli manuel vide les champs et les messages (RG4).** Alternative : conserver la saisie en mémoire tant que la page est ouverte. Position retenue : tout effacer (aucun mot de passe en mémoire dans un panneau caché, cohérent avec `terminerEnvoi()` qui vide déjà les champs après tout envoi).
4. **Focus après une erreur.** Le bouton « Changer le mot de passe » est désactivé pendant l'envoi puis réactivé ; le navigateur peut avoir perdu le focus à ce moment (comportement existant, non modifié ici). Les erreurs sont annoncées par `role="alert"`. Faut-il, après erreur, remettre le focus sur le bouton « Changer le mot de passe » ou sur le premier champ en erreur ? Hors périmètre de R.6 (aucun changement de comportement en cas d'erreur) ; à traiter dans un correctif séparé si la recette le demande.
5. **Message de succès persistant.** Le message reste affiché jusqu'au prochain dépliage, à une nouvelle soumission ou à la sortie de l'écran (pas de disparition automatique). Alternative : disparition après quelques secondes (nécessiterait une minuterie et un test d'horloge).
6. **Section toujours repliée à l'arrivée, sans persistance.** Un rechargement après une erreur replie la section. Position retenue : acceptable (l'état n'est que de l'interface).
7. **Pas de Échap pour replier.** Position retenue : non (même choix que la suppression du compte). Alternative : Échap replie quand le focus est dans le panneau et rend le focus au bouton.
8. **Erreur de mesure des specs précédentes.** Toutes les valeurs de style citées ont été relevées dans `variables.css`, `composants.css`, `page-carte.css`, `formulaire-compte.css`, `suppression-compte.css` et `mon-compte.css` (par exemple `.carte` : gap 20 px et padding 24 px ; `.bouton` : padding 12 px / 20 px ; `--cible-min` : 44 px ; `.formulaire` : gap 16 px). En cas d'écart constaté à l'implémentation, la valeur du code l'emporte et le développeur le signale à l'orchestrateur pour correction de la spec.
9. **Une nouvelle scène dans `aide-theme.ts`** est ajoutée pour que le formulaire déplié reste couvert par les tests de contraste (les scènes `ECRANS` mesurent l'écran replié). C'est un ajout, non une modification d'une scène existante ; le `testeur-e2e` le signale s'il y voit un conflit avec l'interdit de modifier les tests existants.
10. **Taille.** ~90 lignes de production : pas de découpage.
