# Increment 9.4 : Suppression d'un admin

L'admin master peut **supprimer définitivement** un Compte `ADMIN` (actif ou désactivé) depuis l'écran de gestion des administrateurs, après confirmation. Le Compte disparaît de la base et son pseudo est libéré ; toutes ses sessions sont fermées. Sont refusées (409) la suppression de l'admin master et celle du **dernier admin actif**. Un endpoint (`DELETE`), un bouton avec confirmation en ligne (sous-composant du 9.3 réutilisé), aucune migration.

Origine : ligne 9.4 du jalon 9 de `docs/roadmap.md` et « Décisions prises » (suppression physique et pseudo libéré ; coexistence avec la désactivation du 8.1 ; règle du dernier admin du 8.1 étendue à la suppression, l'admin master n'étant pas compté). Cet incrément **revient sur l'exclusion du 8.1** (« pas de suppression d'un Compte `ADMIN` ») et sur 1.5 (`DELETE /api/administration/admins/{id}` jamais 2xx), pour le seul rôle `ADMIN`. Il prolonge le 9.3 (`SupprimerBenevole`), dont il réutilise les mécanismes.

## 2. Règles de gestion

**Domaine et application**
- **RG1** : cible. `DELETE /api/administration/admins/{id}` n'agit que sur un Compte de rôle `ADMIN` ou `ADMIN_MASTER` (`ComptesGeres.ADMINS`). Identifiant inconnu, qui n'est pas un UUID, Compte `BENEVOLE` ou `COUREUR` : 404 `COMPTE_INTROUVABLE`, **réponse identique** (pas d'énumération de rôle), rien n'est modifié. Le rôle est contrôlé par le domaine (`Compte.verifierSuppressionAdmin`, `CompteNonGerableException`), sans règle dupliquée dans le contrôleur. L'état `actif` n'intervient pas dans ce contrôle.
- **RG2** : admin master. Le Compte `ADMIN_MASTER` n'est jamais supprimable : 409 `ADMIN_MASTER_NON_SUPPRIMABLE`, y compris quand l'appelant le vise lui-même. Rien n'est modifié (SEC-08).
- **RG3** : soi-même. Seul l'admin master peut appeler la route (RG11) : le Compte de l'appelant est donc toujours l'admin master et son refus est celui de RG2. **Aucun code `AUTO_SUPPRESSION_INTERDITE`** (inatteignable, point ouvert 3). Un `ADMIN` ne peut pas viser son propre Compte : 403 avant toute résolution.
- **RG4** : dernier admin actif. Si la cible est un `ADMIN` **actif** et qu'il n'existe **aucun autre** Compte `ADMIN` actif : 409 `DERNIER_ADMIN_ACTIF`, rien n'est modifié. L'admin master n'est **pas** compté (décision de la roadmap, 8.1 RG3.3). **Une cible déjà désactivée n'est pas concernée** (elle ne retire aucun admin actif ; cohérent avec 8.1 RG3.3 / RG7) : elle est supprimable même si elle est le seul `ADMIN`, ou si les autres sont désactivés. Conséquence assumée : tant que `Nadia` est le seul `ADMIN` actif, elle n'est pas supprimable. Ordre des refus (le premier l'emporte) : 404 (RG1), admin master (RG2), dernier admin actif (RG4). Même définition d'« autre admin actif » que `verifierDesactivable` (une seule règle dans `Compte`).
- **RG5** : suppression. Pour une cible autorisée, la ligne `compte` est **supprimée physiquement** (`DepotComptes.supprimer`) ; réponse **204** sans corps. Le pseudo et sa clé d'unicité sont libérés : `POST /api/administration/admins` avec le même pseudo (casse différente comprise) est accepté (201, nouvel identifiant, aucun lien avec l'ancien Compte). **Un Compte désactivé (8.1) est supprimable** comme un actif ; aucune désactivation ni réactivation n'est appelée. Aucune affectation, Inscription, Course ni Passage n'est touché (un admin n'en a pas, RG14). Après suppression, la connexion avec l'ancien pseudo donne 401 `IDENTIFIANTS_INVALIDES`, corps identique à celui d'un pseudo inconnu.
- **RG6** : sessions. Après suppression effective, **toutes** les sessions serveur du Compte (tous appareils) sont fermées par `InvalidationAutresSessions.invaliderToutesLesSessions`, **après la validation de la transaction** (`Desactivation.fermerSessionsApresValidation`, jamais si elle est annulée). Les sessions des autres Comptes, dont celle de l'appelant, ne sont pas touchées. Une requête avec l'ancien cookie donne 401 `NON_AUTHENTIFIE`. La connexion concurrente est couverte par la relecture après ouverture de session déjà en place (8.1 RG10 / 9.3 RG6).
- **RG7** : compteur d'échecs. À la suppression effective, `LimitationTentatives.oublier(pseudoNormalise)` : un pseudo réutilisé n'hérite pas d'un blocage 429.
- **RG8** : concurrence. Comme `DesactiverAdmin` (8.1 RG11) : **tous** les Comptes `ADMIN` sont relus sous verrou par `trouverParRolePourModification(ADMIN)` (ordre croissant d'identifiant) avant toute décision ; la cible est prise dans cette liste, sinon par `trouverParIdPourModification` (admin master, ou Compte d'un autre rôle). Conséquences : (a) deux suppressions simultanées de la même cible : un 204, un 404 ; (b) suppression simultanée des deux derniers admins actifs (`Nadia`, `Paul`) : exactement un 204 et un 409 `DERNIER_ADMIN_ACTIF`, jamais zéro admin actif ; (c) suppression et désactivation simultanées (de la même cible ou de deux admins qui seraient les deux derniers actifs) : sérialisées, jamais deux effets qui vident les admins actifs, jamais de 500.
- **RG9** : atomicité. Relecture sous verrou -> garde de domaine (RG1, RG2, RG4) -> `supprimer` -> `oublier` dans **une transaction** ; toute erreur annule tout ; sessions fermées seulement après commit. Panne inattendue : 500 `ERREUR_INTERNE`, Compte inchangé, sessions intactes.
- **RG10** : non-idempotence. Un second `DELETE` sur un Compte déjà supprimé : 404 `COMPTE_INTROUVABLE`.

**Contrat et sécurité**
- **RG11** : sécurité HTTP. `ADMIN_MASTER` seul. `ADMIN`, `BENEVOLE`, `COUREUR` : 403 `ACCES_REFUSE` **avant** toute résolution de `{id}` (même réponse pour un identifiant inconnu) ; anonyme : 401 `NON_AUTHENTIFIE` ; `X-XSRF-TOKEN` absent ou invalide : 403 `CSRF_INVALIDE`, rien modifié. Contrôle côté serveur par la règle existante de `SecuriteConfiguration` (aucune modification). `PUT` et `PATCH` sur `/admins/{id}` restent 404 `RESSOURCE_INTROUVABLE` ou 405. `DELETE /api/administration/benevoles/{id}` vers un `ADMIN` ou l'admin master reste 404 (9.3 RG1). Pas de corps de requête (ignoré).
- **RG12** : erreurs `ProblemDetail` (`application/problem+json`) : `{ "type": "about:blank", "title", "status", "detail", "instance", "code" }`. Codes : `COMPTE_INTROUVABLE` (404, existant), `ADMIN_MASTER_NON_SUPPRIMABLE` (409, nouveau), `DERNIER_ADMIN_ACTIF` (409, **code réutilisé** du 8.1, `detail` propre à la suppression), plus `NON_AUTHENTIFIE`, `ACCES_REFUSE`, `CSRF_INVALIDE`, `ERREUR_INTERNE`. Aucun `detail` ne contient de pseudo, d'identifiant de Compte ni de mot de passe. Le `detail` de la désactivation (« désactiver le dernier administrateur actif ») reste **inchangé** : le cas d'usage de suppression lève une exception distincte, traduite dans `GestionnaireErreurs`.
- **RG13** : journal. Succès : INFO « Admin supprimé (compte `<id>` par `<idAppelant>`) ». Refus 409 : INFO « Suppression refusée (compte `<id>`, motif `<ADMIN_MASTER_NON_SUPPRIMABLE|DERNIER_ADMIN_ACTIF>`) ». Jamais de pseudo ni de mot de passe. 404 et 403 : aucune ligne INFO de ce cas d'usage.
- **RG14** : persistance et architecture. **Aucun changeset**. Pas de port de désaffectation (un admin n'a aucune affectation de Course) : `SupprimerAdmin` ne dépend que de `DepotComptes`, `InvalidationAutresSessions`, `RegistreTentativesConnexion`, `PolitiqueBlocage`. **Hypothèse à vérifier au 9.7** : aucun `ADMIN` n'a d'Inscription avant le changement de rôle ; si le 9.7 en crée, la suppression doit être revue (point ouvert 2). Aucune règle dupliquée : la recherche de la cible dans la liste verrouillée (`parmi`) est factorisée avec `DesactiverAdmin` (ex. dans `ComptesGeres` ou un utilitaire du package), la notion d'« autre admin actif » reste unique dans `Compte`. ArchUnit inchangé.

**Front**
- **RG15** : bouton. Sur `/administration/admins`, chaque ligne (Compte actif **et** désactivé) porte `admin-bouton-supprimer`, après Désactiver / Réactiver. L'admin master n'est pas dans la liste, donc sans bouton. `ADMINS.suppression` est renseigné ; `BENEVOLES.suppression` et l'écran des bénévoles sont inchangés. Le bouton est une aide d'affichage : le contrôle réel est RG11. Cibles de 44 px, contraste et focus de `docs/design.md`.
- **RG16** : confirmation. Un clic sur « Supprimer » n'émet **aucun appel réseau** et ouvre `admin-suppression-confirmation` avec `admin-suppression-confirmation-texte` : « Supprimer définitivement l'administrateur <pseudo> ? Son compte sera supprimé, son pseudo pourra être réutilisé et ses sessions seront fermées. Cette action est irréversible. » ; boutons `admin-suppression-bouton-confirmer` (« Confirmer la suppression ») et `admin-suppression-bouton-annuler`. Une seule confirmation ouverte à la fois, toutes actions confondues (mécanisme du 9.3). Pseudo en texte, focus sur « Annuler » à l'ouverture, Échap ferme, focus rendu à « Supprimer ». Confirmer : `GET /api/csrf` puis `DELETE` ; boutons désactivés pendant l'envoi (un double clic n'émet qu'un `DELETE`).
- **RG17** : après l'action. Succès (204) : confirmation fermée, liste rechargée (la ligne disparaît), `admin-message-action` « L'administrateur <pseudo> a été supprimé. ». Erreurs (`admin-erreur-action`, confirmation fermée) : 409 `DERNIER_ADMIN_ACTIF` « Impossible : c'est le dernier administrateur actif. » (liste rechargée) ; 409 `ADMIN_MASTER_NON_SUPPRIMABLE` « Impossible : l'administrateur principal ne peut pas être supprimé. » (liste rechargée) ; 404 `COMPTE_INTROUVABLE` « Ce compte n'existe plus. » (liste rechargée) ; 403 `CSRF_INVALIDE` « La page a expiré, veuillez réessayer. » (nouveau jeton, liste non rechargée) ; 403 `ACCES_REFUSE` : `/acces-refuse` ; 401 : `/connexion?retour=%2Fadministration%2Fadmins` ; 5xx ou réseau : « Service indisponible, veuillez réessayer plus tard. ». ## 3. Cas limites

- **Admin master visé** (appel direct, par lui-même, seul appelant possible) : 409 `ADMIN_MASTER_NON_SUPPRIMABLE`, même s'il est le seul Compte restant (RG2 avant RG4).
- **`Nadia` seule `ADMIN` actif** : 409 `DERNIER_ADMIN_ACTIF`. **`Nadia` et `Paul` actifs** : `Paul` supprimé (204), puis `Nadia` : 409.
- **`Nadia` active + `Paul` désactivé** : `Paul` supprimable (204, cible inactive) ; `Nadia` : 409 (aucun autre actif, `Paul` inactif ne compte pas).
- **Seul `ADMIN` désactivé** (état posé en base, ex. après des suppressions) : supprimable, 204 (RG4).
- **Deux admins actifs, suppression simultanée des deux** : un 204, un 409 (RG8b).
- **Cible d'un autre rôle** : `BENEVOLE` (`Léo`), `COUREUR` (`Alice`), inconnu, `pas-un-uuid` : 404 identique (RG1).
- **Appelant `ADMIN`** (`Nadia`) : 403 pour une cible existante comme inconnue ; l'écran n'est pas accessible (garde existant).
- **Pseudo réutilisé** : accepté après suppression ; le nouvel admin n'hérite d'aucune session ni blocage (RG5, RG7).
- **Session ouverte de l'admin supprimé** : 401 au clic suivant ; le front la renvoie vers `/connexion` via `GET /api/comptes/moi` (déjà en place).
- **Plusieurs Courses en parallèle, boucle courante, bascule de Boucle, dernière boucle, vainqueurs partagés, Course complète ou non démarrée, coureur réintégré, `CORRECTION` / `SCAN`, Inscription sans Passage, bénévole non affecté** : non applicables, l'incrément ne touche ni Course, ni Inscription, ni Passage. Distance, dénivelé, allure, boucles terminées, durée écoulée : inchangés.

## 4. Contrat d'API

Toutes les erreurs sont des `ProblemDetail` (`application/problem+json`). Tout endpoint peut aussi répondre 500 `ERREUR_INTERNE` (rien modifié).

### DELETE /api/administration/admins/{id} (nouveau)
- Rôle : `ADMIN_MASTER`. En-tête `X-XSRF-TOKEN` obligatoire. `{id}` : identifiant (UUID, chaîne) du Compte `ADMIN`. Pas de corps de requête ni de réponse en cas de succès.
- **204** : Compte supprimé, sessions fermées (RG5, RG6).
- **401** `NON_AUTHENTIFIE`. **403** `ACCES_REFUSE` (`ADMIN`, `BENEVOLE`, `COUREUR`, avant résolution de `{id}`). **403** `CSRF_INVALIDE`.
- **404** `COMPTE_INTROUVABLE` : `{ "title": "Introuvable", "status": 404, "detail": "Ce compte est introuvable.", "code": "COMPTE_INTROUVABLE" }` (inconnu, mal formé, déjà supprimé, `BENEVOLE`, `COUREUR`).
- **409** `ADMIN_MASTER_NON_SUPPRIMABLE` : `{ "type": "about:blank", "title": "Conflit", "status": 409, "detail": "L'administrateur principal ne peut pas être supprimé.", "instance": "/api/administration/admins/<id>", "code": "ADMIN_MASTER_NON_SUPPRIMABLE" }`.
- **409** `DERNIER_ADMIN_ACTIF` : même forme, `"detail": "Impossible de supprimer le dernier administrateur actif."`, `"code": "DERNIER_ADMIN_ACTIF"`.
- 400 : non applicable. `PUT`, `PATCH` sur le même chemin : 404 `RESSOURCE_INTROUVABLE` ou 405, jamais 2xx.

### Endpoints inchangés
`GET` et `POST /api/administration/admins`, `POST .../{id}/desactivation` (détail 409 `DERNIER_ADMIN_ACTIF` inchangé : « Impossible de désactiver le dernier administrateur actif. »), `POST .../{id}/reactivation`, tous les endpoints bénévoles ; `CompteReponse` inchangé.

### Ports internes (non exposés)
Aucun nouveau port : `DepotComptes.supprimer(UUID)` existant.

## 7. Tester à la main

Prérequis : `docker compose up -d --build` (`base`, `api`, `web` sains), http://localhost, `.env` avec `ADMIN_MASTER_PSEUDO=Patron`, `ADMIN_MASTER_MOT_DE_PASSE=mot-de-passe-patron-1`, puis `./scripts/donnees-demo.sh` (`Nadia`, `mot-de-passe-admin-1`, seul `ADMIN`). Les admins jetables ont pour mot de passe `mot-de-passe-jetable-1`.

1. Préparation : en `Patron`, menu « Admins », « Nouvel admin » : créer `JetableA`, `JetableB`, `JetableC` (le formulaire se referme après chaque création). Chaque ligne (`Nadia` comprise) affiche « Actif », « Désactiver », « Supprimer ». `Patron` n'est pas dans la liste.
2. Annuler : « Supprimer » pour `JetableA` : confirmation avec l'avertissement (suppression définitive, pseudo réutilisable, sessions fermées) ; rien n'a changé. « Annuler » la ferme. « Supprimer » puis « Désactiver » sur la même ligne : une seule confirmation reste ouverte.
3. Suppression : « Supprimer » puis « Confirmer la suppression » pour `JetableA` : message « L'administrateur JetableA a été supprimé. », ligne disparue. Fenêtre privée : connexion `JetableA` / `mot-de-passe-jetable-1` : « Pseudo ou mot de passe incorrect. ». Recréer `JetableA` (mot de passe `mot-de-passe-jetable-2`) : accepté, connexion possible.
4. Session ouverte et compte désactivé : fenêtre privée A : se connecter en `JetableB` (page d'administration). En `Patron` : « Désactiver » `JetableB` (confirmer), puis le bouton « Supprimer » reste disponible sur la ligne désactivée : le supprimer. Fenêtre A : F5 ou clic sur un lien : retour à la connexion.
5. Dernier admin actif : supprimer `JetableA` puis `JetableC` : acceptés (`Nadia` reste active). Il ne reste que `Nadia` : « Supprimer » `Nadia` puis confirmer : « Impossible : c'est le dernier administrateur actif. », `Nadia` toujours dans la liste. Créer `JetableD`, le désactiver : supprimer `Nadia` reste refusé (un admin désactivé ne compte pas) ; supprimer `JetableD` (désactivé) : accepté.
6. Admin master : récupérer l'identifiant de `Patron` (`curl -b jar http://localhost/api/comptes/moi` après connexion, jar de cookies comme 3.1 §7), obtenir un jeton (`GET /api/csrf`, cookie `XSRF-TOKEN`), `curl -b jar -X DELETE -H "X-XSRF-TOKEN: <jeton>" http://localhost/api/administration/admins/<idPatron>` : 409 `ADMIN_MASTER_NON_SUPPRIMABLE`. Avec un identifiant bidon ou celui de `Léo` : 404 `COMPTE_INTROUVABLE` ; sans l'en-tête : 403 `CSRF_INVALIDE`.
7. Droits : en `Nadia`, http://localhost/administration/admins : accès refusé ; l'entrée « Admins » n'est pas dans le menu. Même `curl` avec la session de `Nadia` : 403 `ACCES_REFUSE`. En `Léo` ou `Alice` : accès refusé.
8. Base : `docker compose exec base psql -U backyard -d backyard -c "select pseudo, role, actif from compte where role like 'ADMIN%'"` ne montre plus les jetables supprimés ; `select id from databasechangelog` : pas de nouveau changeset (dernier `0011-compte-actif`).
9. Journal : `docker compose logs api | grep -E "Admin supprimé|Suppression refusée"` montre des identifiants et les motifs ; `docker compose logs api | grep -iE "Jetable|Nadia|mot-de-passe"` ne retourne rien de ces lignes.
10. Remise à zéro : `docker compose down -v` puis `docker compose up -d --build`.

## 8. Points ouverts

Bloquants : aucun. Positions par défaut appliquées dans la spec.

1. **Taille.** ~115 lignes de production (back ~85, front ~30) : un seul incrément, aucun découpage.
2. **Question en attente n°2 de la roadmap (admin issu d'un coureur).** Hors périmètre ici : avant le 9.7 aucun `ADMIN` n'a d'Inscription (admins créés par l'admin master), donc la suppression physique ne laisse aucune référence orpheline. Après le 9.7, un `ADMIN` issu d'un coureur peut avoir des Inscriptions `TERMINEE` conservées : sa suppression physique les laisserait pointer vers un Compte absent. À trancher **avant le 9.6/9.7** (recommandation de la roadmap : anonymiser le Compte s'il a des Inscriptions, supprimer physiquement sinon) ; `SupprimerAdmin` devra alors être revu (dépendance vers `courses` par un port, comme `DesaffectationBenevole`). RG14 consigne l'hypothèse.
3. **Soi-même.** Seul l'admin master appelle la route et il est protégé par RG2 : pas de code `AUTO_SUPPRESSION_INTERDITE` (inatteignable, contrairement à `AUTO_DESACTIVATION_INTERDITE` du 8.1 qui reste défini par défense en profondeur). Alternative : l'ajouter par symétrie, sans effet observable. À confirmer.
4. **Cible désactivée et « dernier admin ».** Retenu (cohérent avec 8.1 RG3.3 / RG7) : un `ADMIN` déjà désactivé est supprimable même s'il est le seul `ADMIN`, car il ne retire aucun admin actif. Conséquence : on peut arriver à zéro `ADMIN` (l'admin master seul) par cette voie ; il en crée alors un autre. Alternative : compter aussi les inactifs pour interdire de vider la liste. À confirmer.
5. **Conséquence de la règle.** `Nadia`, seul `ADMIN` actif de la démo, n'est pas supprimable tant qu'aucun autre `ADMIN` actif n'existe ; l'admin master crée d'abord un autre admin.
6. **Code et détail du refus « dernier admin ».** Retenu : code `DERNIER_ADMIN_ACTIF` réutilisé, `detail` propre à la suppression (le front distingue l'action par son appel, pas par le code). Alternative : un code distinct `DERNIER_ADMIN_ACTIF_SUPPRESSION`. À confirmer.
7. **Données de démo.** Script et `donnees-demo.spec.ts` inchangés (la roadmap prévoit « à ajouter plus tard » un admin jetable) : la recette en crée par l'interface, comme au 9.3. Alternative : un `Jetable` dans le script (disparaît après la première recette). À confirmer.
8. **Libellés et identifiants.** Code `ADMIN_MASTER_NON_SUPPRIMABLE`, textes de confirmation et d'erreur, `data-testid` `admin-bouton-supprimer` et `admin-suppression-*`, message « L'administrateur <pseudo> a été supprimé. ». À confirmer.
9. **Textes antérieurs remplacés.** 1.5 (`DELETE /admins/{id}` jamais 2xx), 8.1 §1 (« pas de suppression ») et 9.3 §1 / CA9 (`DELETE /admins/{id}` : 404 ou 405 pour `Patron`) sont remplacés pour le rôle `ADMIN` ; ces specs ne sont pas modifiées (historique), RG18 consigne les tests à mettre à jour.
