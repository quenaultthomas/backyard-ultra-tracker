Aucune valeur secrète. (b) Le tableau des variables de `docs/deploiement.md` gagne une ligne `BACKYARD_PHOTOS_REPERTOIRE` : « fixe (`/donnees/photos`), non réglable » avec le rôle « répertoire des fichiers de photos de profil, point de montage du volume `photos` (voir Sauvegarde et Restauration) ». (c) `docker-compose.yml` n'est pas modifié ; la valeur documentée est celle du compose.
- **RG8 [doc]** : décision de modération et de confidentialité (MET-09). Consignée dans `docs/roadmap.md`, section « Décisions prises », **une ligne** « Modération des photos » : les photos de profil restent retirables par leur **seul propriétaire** (retrait à tout moment, suppression ou anonymisation du Compte) ; **aucune action admin « retirer la photo »** n'est ajoutée dans ce correctif (reportée à un incrément ultérieur si le besoin se confirme) ; en cas d'urgence l'exploitant dispose de la procédure de `docs/deploiement.md` (RG9) ; l'information de confidentialité existe déjà (phrase de Mon compte, 10.1b RG19) et le retrait d'une photo peut rester visible **jusqu'à 5 minutes** dans un navigateur qui l'a déjà en cache (10.2 RG5). Incrément concerné : 10.1b, 10.2. Les points ouverts 8 et 9 de 10.2 et 6 de 10.1 sont réputés tranchés par cette ligne.
- **RG9 [doc]** : procédure d'urgence de retrait d'une photo (MET-09). Section « Retirer une photo en urgence » de `docs/deploiement.md` (en `$PROD`, comme les autres procédures), trois étapes : (1) **identifier** le Compte : `$PROD exec base psql -U backyard -d backyard -c "select id, photo_jeton, photo_format from compte where pseudo = '<pseudo>'"` (le pseudo est visible sur le polaroïd) ; (2) **retirer de l'affichage** : `$PROD exec base psql -U backyard -d backyard -c "update compte set photo_jeton = null, photo_format = null where pseudo = '<pseudo>'"` (les deux colonnes ensemble : la contrainte `ck_compte_photo_coherente` l'exige) ; dès cette instruction l'adresse répond 404 et le suivi renvoie `photoUrl` `null` (silhouette au rafraîchissement suivant, au plus ~4 s) ; (3) **supprimer le fichier** : `$PROD exec api rm /donnees/photos/<photo_jeton>.<ext>` (`<ext>` : `png` pour `PNG`, `jpg` pour `JPEG`, `webp` pour `WEBP`). Mentions obligatoires : un navigateur qui a déjà la photo peut l'afficher jusqu'à 5 minutes (recharger l'écran projeté avec un rechargement forcé) ; si l'étape 3 est oubliée, le fichier devenu orphelin est supprimé au prochain démarrage de `api` (RG4 à RG6) ; la procédure contourne l'application (aucune ligne de journal applicatif) ; elle ne touche ni le Compte, ni les Inscriptions, ni les sessions.

### Back

- **RG2 [back]** : `HEAD /api/photos/*` compté par la limite de débit (ARC-02). Le mécanisme de limite de débit public (7.2, 10.2 RG6) devient paramétrable par **méthodes comptées** : pour le préfixe `/api/photos`, **`GET` et `HEAD`** sont comptés dans le même compteur (par IP, fenêtre fixe d'une minute, plafond `BACKYARD_LIMITE_DEBIT_PHOTOS_PAR_MINUTE`, 0 = pas de limite) ; pour le préfixe `/api/courses`, seul `GET` est compté (**inchangé**, `HEAD` non compté, donc jamais de 429 ; un `HEAD` anonyme sur ces routes répond 401 car `SecuriteConfiguration` n'y ouvre que `GET`, comportement inchangé). Un `HEAD` refusé reçoit le 429 `TROP_DE_REQUETES` habituel (en-têtes `Retry-After`, `Cache-Control: no-store` ; pas de corps pour un `HEAD`), **avant** tout accès base ou disque. Aucune autre méthode n'est comptée (`OPTIONS`, `POST`, etc. : inchangé). Une seule implémentation du mécanisme (pas de copie).
- **RG3 [back]** : l'ETag est évalué avant la lecture du fichier (PER-04). (a) Le cas d'usage de lecture est scindé en deux étapes : **résolution** (contrôle de forme du jeton, une recherche SQL, renvoie le jeton et le format ou lève `PhotoIntrouvableException`) puis **lecture des octets** (appelée seulement si nécessaire). La résolution ne touche pas au stockage de fichiers. (b) L'exposition évalue `If-None-Match` contre l'ETag `"<jeton>"` **entre les deux étapes** : s'il correspond (mêmes règles de comparaison qu'aujourd'hui : valeur entre guillemets, liste de valeurs, `*`, forme faible `W/`), la réponse est **304** sans corps avec `ETag` et `Cache-Control: public, max-age=300`, et **le fichier n'est pas lu**. Sinon, lecture puis 200. (c) Coûts garantis par requête : jeton mal formé = 0 SQL, 0 lecture ; jeton inconnu / retiré = 1 SQL, 0 lecture ; 304 = 1 SQL, 0 lecture ; 200 = 1 SQL, 1 lecture. **Exception, chemin d'anomalie seulement** : quand le fichier est manquant à la lecture, le journal ERROR « Fichier de photo introuvable (compte `<id>`) » (10.1 RG14) exige l'identifiant du Compte, que la référence résolue ne transporte pas ; le Compte est alors **relu (une recherche supplémentaire) uniquement sur ce chemin**, jamais pour un 200, un 304 ou un 404 ordinaire. (d) **Comportement HTTP externe inchangé** : codes 200 / 304 / 404 / 429, tous les en-têtes de 10.2 §4, corps du 404 identique. Seule nuance assumée : si la base porte un jeton dont le fichier a disparu du volume, une revalidation avec ETag correspondant donne 304 (le navigateur garde sa copie) ; un chargement sans ETag donne 404 + ERROR comme avant (10.1 RG7, RG14). (e) `HEAD` suit le chemin du `GET` (lecture du fichier pour `Content-Length`) ; il est borné par RG2. (f) Aucune règle métier dans le contrôleur : la comparaison d'ETag est une règle HTTP d'exposition, la résolution et la lecture sont dans le cas d'usage.
- **RG4 [back]** : nettoyage des fichiers orphelins : sélection (ARC-07). La règle de sélection est portée par le **domaine** `comptes` (Java pur, `Clock` injecté, aucune dépendance de framework). Elle examine les entrées **directes** du répertoire des photos (sans descendre dans les sous-répertoires, sans suivre les liens symboliques ; les répertoires et liens sont ignorés) et classe chaque fichier régulier : (a) **fichier de photo conforme** : nom `^[0-9a-f]{32}\.(png|jpg|webp)$` ; il est **orphelin** si son jeton n'est porté par **aucun** Compte ; il est supprimé s'il est orphelin **et** modifié depuis plus de **1 heure** (seuil constant, `Clock`) — la marge protège un envoi en cours dont la transaction n'est pas encore validée ; (b) **fichier temporaire de l'adaptateur** : nom `^[0-9a-f]{32}\.(png|jpg|webp)\.tmp$` ; supprimé s'il est modifié depuis plus de 1 heure (quel que soit l'état de la base) ; (c) **tout autre nom est ignoré, jamais supprimé** (`.gitkeep`, `notes.txt`, majuscules, 31 ou 33 caractères hexadécimaux, extension inconnue, `.tmp` d'un autre format) ; (d) **un fichier dont le jeton est porté par un Compte n'est jamais supprimé**, y compris si son extension diffère du `photo_format` du Compte (incohérence : conservé, compté parmi les « ignorés », sans suppression). La base est interrogée par **une seule instruction** pour l'ensemble des jetons conformes trouvés (aucune requête par fichier).
- **RG5 [back]** : nettoyage : tolérance et journal. (a) Le nettoyage **ne bloque jamais** le démarrage et ne lève aucune exception vers l'appelant. (b) Une erreur sur un fichier (suppression impossible, fichier disparu entre-temps) : on passe au suivant, comptée. (c) Une erreur de lecture du répertoire (droits, ce n'est pas un répertoire) : WARN unique, aucun fichier supprimé. (d) Une erreur d'accès à la base : WARN unique, **aucun fichier supprimé** (jamais de suppression sans connaître les jetons portés). (e) **Journal** : une ligne INFO de bilan « Nettoyage des photos : N fichier(s) orphelin(s) supprimé(s), M fichier(s) temporaire(s) supprimé(s), K fichier(s) ignoré(s) » ; un WARN « Nettoyage des photos : E erreur(s) » si E > 0. **Jamais** de jeton, de nom ou de chemin de fichier, de pseudo, d'identifiant de Compte ni d'octets dans ces lignes (seulement des nombres). Aucune ligne INFO ou supérieure par fichier. (f) Aucune écriture en base.
- **RG6 [back]** : nettoyage : déclenchement et répertoire. (a) Exécuté **une fois au démarrage de `api`**, après l'application des migrations Liquibase et la disponibilité de la base, par un déclencheur d'infrastructure qui appelle le cas d'usage (aucun Spring dans le cas d'usage hors stéréotype et transaction). (b) **Répertoire absent** (volume neuf, jamais écrit) : rien à nettoyer, **le répertoire n'est pas créé** par le nettoyage, bilan « 0, 0, 0 », aucun WARN. (c) **Répertoire vide** : bilan « 0, 0, 0 ». (d) Un seul balayage par démarrage (pas de planificateur) ; un redémarrage de `api` relance un balayage. (e) Procédure d'exploitation dans `docs/deploiement.md` (nouvelle section « Photos de profil : nettoyage au démarrage ») : objet, règle (RG4), seuil d'une heure, lecture du bilan avec `$PROD logs api | grep "Nettoyage des photos"`, **ordre de restauration** (restaurer la base **avant** de démarrer `api` avec un volume restauré : sinon les fichiers restaurés dont le jeton n'est pas encore en base seraient vus comme orphelins ; voir aussi RG7), conduite à tenir si le bilan signale des erreurs, et le fait qu'un fichier laissé par un échec d'effacement (10.1 RG9) est rattrapé au redémarrage suivant, au plus une heure après son dépôt.
- **RG7 [back]** : nettoyage : garde-fou. Si le nombre de fichiers à supprimer au titre de (4a) **dépasse 10 et dépasse la moitié** des fichiers de photo conformes du répertoire, **rien n'est supprimé** : WARN « Nettoyage des photos suspendu : trop de fichiers orphelins (N sur T) » (nombres seulement) ; l'exploitant décide (typiquement : base restaurée à une date antérieure, ou volume restauré sans la base). Les fichiers temporaires (4b) sont supprimés indépendamment du garde-fou. En deçà des seuils, le nettoyage supprime tous les orphelins. Les seuils (10 et la moitié) sont des constantes du domaine.
- **RG12 [back]** : construction de l'adresse de la photo dans l'exposition (ARC-02). (a) Le cas d'usage `ConsulterSuivi` et le port d'annuaire des photos ne manipulent que le **jeton** : le champ de `CoureurSuivi` devient `jetonPhoto` (texte de 32 caractères hexadécimaux ou `null`) ; aucun préfixe d'URL dans le domaine ni l'application de `courses`. (b) `SuiviCourseReponse` (exposition de `courses`) construit `photoUrl` = `/api/photos/` + jeton, ou `null` si le jeton est `null`. **Le JSON du suivi est strictement inchangé** (22 champs de premier niveau, lignes `dossard`, `pseudo`, `photoUrl`). (c) `partage.domaine.AdressePhoto` est **supprimée** ; `partage.domaine` ne contient plus que `FormatImage`. Aucune classe de `domaine` ou d'`application` ne contient la route des photos. La route n'existe plus que dans l'exposition (contrôleur de lecture et DTO de `comptes`, DTO du suivi de `courses`) et dans l'infrastructure de `courses` (filtre de limite de débit), **chaque couche gardant sa propre constante** : aucun nouveau paquet partagé, **aucune nouvelle autorisation ArchUnit** (les règles existantes passent sans modification, point ouvert 1). (d) La cohérence des constantes est garantie par un test d'intégration (CA18) : l'adresse publiée par le suivi est servie par le contrôleur de lecture et comptée par la limite de débit des photos. (e) `GET /api/comptes/moi` : `photoUrl` inchangé (construit dans l'exposition de `comptes`).
- **RG13 [doc]** : référentiel d'audit. `docs/audits/referentiel.md` gagne **7 lignes** (les 7 points de la section « Propositions d'ajout au référentiel » du rapport), avec des identifiants **nouveaux**, jamais repris (convention du fichier : on ajoute, on ne réutilise ni ne renumérote ; derniers identifiants existants : SEC-22, MET-15, PER-05, DEP-08, FRT-07) : **SEC-23** (envoi de la photo de profil, P1, 10.1a), **SEC-24** (lecture publique de `GET /api/photos/{jeton}`, `HEAD` compris dans la limite, P1, 10.1a), **MET-16** (effacement de la photo après validation à la suppression, l'anonymisation, le remplacement ou le retrait, P1, 10.1a), **PER-06** (cohérence base / volume des photos, P2, 10.1a), **DEP-09** (volume `photos`, P2, 10.1a), **PER-07** (charge du suivi public : requêtes SQL et lectures disque, P2, 10.2), **FRT-08** (écran Mon compte, préparation de la photo, P2, 10.1b). ### Front

- **RG10 [front]** : nouvelle tentative d'une photo en échec (FRT-02). Remplace 10.2 RG10 pour « aucune nouvelle tentative ». Quand le chargement de l'image d'un polaroïd échoue (événement `error` : 404, 429, 5xx, réseau), la silhouette est affichée immédiatement (inchangé) **et** une nouvelle tentative est planifiée pour **la même adresse** : (a) délais successifs depuis l'échec précédent : **30 s**, puis **2 min**, puis **5 min** ; **3 nouvelles tentatives au plus par adresse** (soit 4 requêtes au total), puis plus aucune : la silhouette reste jusqu'à un changement de `photoUrl` ou un rechargement de la page ; (b) la tentative **réutilise le même nœud DOM** `img` du polaroïd (pas de recréation du polaroïd, 10.2 RG11b) et la **même adresse exacte** (aucun paramètre ajouté : l'ETag et le cache HTTP jouent normalement) ; (c) si la tentative réussit, la photo remplace la silhouette, sans message ; si elle échoue, on passe au délai suivant ; (d) **aucune tentative pendant que l'onglet est caché** (`document.hidden`) : l'échéance est reportée au retour de l'onglet à l'état visible, la tentative part alors aussitôt et ne consomme pas d'essai tant qu'elle n'a pas été émise ; (e) le compteur d'essais est **par adresse** : un changement de `photoUrl` pour ce dossard annule la tentative planifiée, remet le compteur à zéro et charge la nouvelle adresse normalement ; (f) un polaroïd retiré (abandon) ou le composant détruit **annule** sa tentative planifiée (aucune requête après disparition) ; (g) les délais et le plafond sont des constantes uniques du composant polaroïd ; (h) aucun message d'erreur affiché pour une photo, aucune exception dans la console.
- **RG11 [front]** : le polling du suivi n'émet toujours **aucune** requête d'image (10.2 RG11 inchangée) : seules les tentatives de RG10 en émettent, et seulement pour une adresse en échec. `photoUrl` `null` ou ne commençant pas par `/api/photos/` : silhouette, **jamais de tentative** (la garde défensive de 10.2 RG10 est conservée). Le préfixe `/api/photos/` recopié dans `polaroid-coureur.ts` reste une **garde défensive documentée** (commentaire à jour : copie volontaire, le front ne partage pas de constante avec le back) ; aucun changement de ce côté (ARC-02, partie front du rapport).

## 3. Cas limites

- **Instants exacts de bascule de Boucle, dernière Boucle autorisée, aucun Passage (vainqueurs partagés), Course complète, Passage `SCAN` ou `CORRECTION`, coureur réintégré, bénévole non affecté, rôle insuffisant** : **non applicables** à ce correctif (aucun calcul de Boucle, distance, dénivelé, allure ni durée n'est touché, aucun endpoint de rôle ajouté). Les lectures de photo et de suivi sont publiques.
- **Course non démarrée, Inscription sans aucun Passage, plusieurs Courses en parallèle** : sans effet sur RG2, RG3, RG4 à RG7 (les photos ne dépendent d'aucune Course). Pour RG12 : un coureur inscrit à deux Courses a le même jeton, donc la même adresse dans les deux suivis (inchangé).
- **RG2** : `HEAD` et `GET` d'une même IP partagent le compteur des photos (3 `HEAD` + 2 `GET` avec un plafond de 5 : le 6e appel de n'importe quelle méthode est refusé) ; `HEAD /api/courses/X/suivi` ou `/logo` n'est toujours pas compté (réponse 401 anonyme, jamais 429) ; une nouvelle minute remet le compteur à zéro ; limite 0 : rien n'est refusé, `HEAD` compris.
- **RG3** : `If-None-Match` avec valeur faible `W/"<jeton>"`, liste `"x", "<jeton>"`, `*` : 304 sans lecture ; valeur d'un ancien jeton (photo remplacée) : le jeton de l'URL ne correspond pas au Compte, 404 ; jeton retiré avec `If-None-Match` correspondant : **404** (la base fait foi, la résolution échoue avant l'ETag, jamais de 304 pour une photo retirée) ; fichier manquant avec ETag correspondant : 304 (RG3d) ; fichier manquant sans ETag : 404 + ERROR, avec une relecture du Compte (2 instructions SQL) propre à ce chemin d'anomalie (RG3c).

## 4. Contrat d'API

**Aucun nouvel endpoint, aucun DTO nouveau, aucun champ ajouté ou retiré, aucune variable d'environnement nouvelle.** Le JSON de toutes les réponses est **inchangé**. Seuls des comportements précisés ci-dessous. Format d'erreur : `ProblemDetail` existant.

### `GET /api/photos/{jeton}` et `HEAD /api/photos/{jeton}` (public, aucun rôle)

| Code | Condition | Précisions modifiées par ce correctif |
|---|---|---|
| 200 | jeton en base, fichier présent, `If-None-Match` absent ou non correspondant | inchangé (corps = octets pour `GET`, aucun corps pour `HEAD`) ; en-têtes de 10.2 §4 |
| 304 | `If-None-Match` correspond à `"<jeton>"` | **le fichier n'est pas lu** (RG3) ; `ETag` et `Cache-Control: public, max-age=300`, sans corps |
| 404 `PHOTO_INTROUVABLE` | jeton mal formé (0 SQL), inconnu, retiré, Compte supprimé, ancien jeton, fichier manquant (sans ETag correspondant) | inchangé, `Cache-Control: no-store` ; la photo retirée donne 404 même avec un `If-None-Match` correspondant |
| 429 `TROP_DE_REQUETES` | plus de `BACKYARD_LIMITE_DEBIT_PHOTOS_PAR_MINUTE` requêtes **`GET` ou `HEAD`** dans la minute depuis la même IP | **`HEAD` désormais compté** (RG2) ; `Retry-After` >= 1, `Cache-Control: no-store` ; sans corps pour `HEAD` |

Aucun 400 applicatif, 401, 403, 409 (les séquences de traversée gardent le comportement de 10.1 RG7).

### `GET /api/courses/{id}/suivi` (inchangé)

Réponse, codes et en-têtes inchangés. `coureursEnCourse[].photoUrl` et `vainqueurs[].photoUrl` : `/api/photos/<32 hex minuscules>` ou `null`, construits par l'exposition (RG12). `HEAD` sur `/api/courses/**` : toujours non compté par la limite de débit, et toujours 401 pour un anonyme (seul `GET` est ouvert).

### `GET /api/comptes/moi` (inchangé)

`photoUrl` inchangé.

### Configuration

Aucune variable ajoutée. `BACKYARD_PHOTOS_REPERTOIRE` est documentée comme valeur fixe (RG1). Le seuil d'une heure et les seuils du garde-fou (RG4, RG7) sont des constantes du domaine, non réglables.

## 5. Écrans

### Suivi d'une Course (`/courses/:id/suivi`, public) : seul écran concerné

- Mon compte, pilotage, liste des Courses : inchangés.

## 8. Points ouverts

À remonter à l'utilisateur ; chaque point a une position par défaut qui permet de commencer (positions par défaut acceptées par l'orchestrateur).

1. **Constante de la route des photos (RG12).** Position par défaut : **trois constantes** (contrôleur de `comptes`, DTO du suivi de `courses`, filtre de limite de débit de `courses`), liées par le test d'intégration CA18 ; zéro nouvelle exception ArchUnit, comme demandé. Alternative : un petit paquet partagé `partage.exposition` (constante unique), mais il demande une autorisation ArchUnit de plus et pose un problème de sens de dépendance pour l'infrastructure.
2. **Seuil d'une heure et garde-fou (RG4, RG7).** Position par défaut : seuil fixe d'1 h (protège un envoi en cours) et suspension si plus de 10 fichiers à supprimer et plus de la moitié des fichiers conformes. Le garde-fou protège le cas « volume restauré avant la base » (la restauration conserve les dates des fichiers). Alternatives : seuils réglables par variable ou pas de garde-fou.
3. **Balayage au démarrage seulement.** Un fichier laissé par un échec d'effacement reste sur le volume jusqu'au prochain redémarrage de `api`. Un balayage périodique serait nécessaire pour une promesse de suppression plus stricte. Position par défaut : non.
4. **`HEAD` lit toujours le fichier (RG3e).** `HEAD` est compté (RG2) mais exécute encore la lecture complète pour `Content-Length`. Alternative : répondre avec la taille du fichier sans lecture. Non retenu.
5. **304 pour un fichier manquant (RG3d).** Avec un ETag correspondant et un fichier disparu du volume, la réponse est 304 au lieu de 404, conséquence assumée de « un 304 ne lit jamais le fichier ».
6. **Délais de nouvelle tentative (RG10).** 30 s, 2 min, 5 min (3 nouvelles tentatives, 4 requêtes au total par adresse). Un échec de plusieurs heures laisse la silhouette jusqu'au rechargement.
7. **Information de confidentialité à l'inscription à une Course et action admin « retirer la photo ».** Hors périmètre (RG8) ; à reporter si l'utilisateur le souhaite.
8. **Procédure d'urgence (RG9).** Elle contourne l'application (pas de journal applicatif, pas d'invalidation de session). Acceptable ; une action admin la remplacerait si elle est un jour demandée.
9. **Libellés du référentiel (RG13).** SEC-24 (« `HEAD` compris dans la limite ») n'est vrai qu'après RG2 ; PER-06 (« photos manquantes détectées ») n'est vrai qu'à la lecture (ERROR), pas par le balayage. Conservés tels que dans le rapport.
10. **Pas de découpage proposé** : ~240 lignes de production, relisible en une fois.
